# 학생 팀 협업 안내

## 현재 저장소 상태

설정 작성 전 현재 커밋은 파일이 없는 초기 상태였습니다. 기존 앱 코드·기술 스택·의존성 정의·실행 안내·지침·양식·자동 검사 설정이 없어 덮어쓴 기존 파일은 없습니다.
실행·테스트·린트(코드 규칙 검사)·빌드(실행 결과물 생성) 명령은 아직 정의되어 있지 않습니다. 임의의 명령을 실행하지 말고, 앱 코드가 도입되면 실제 설정을 확인해 이 안내에 추가하세요.

## 함께 작업하는 순서

1. GitHub에서 기능 요청 또는 버그 신고 양식으로 이슈를 만드세요. 원하는 동작과 완료 조건(어떻게 확인하면 끝인지)을 작게 정하세요. 버그는 기대한 결과를 완료 기준으로 삼으세요.
2. 팀에서 담당자 **한 명**을 정해 이슈의 담당자(Assignees)에 지정하세요. 양식이 자동으로 지정하지는 않습니다.
3. 담당자는 Copilot 앱에서 이슈별 별도 브랜치와 작업 공간을 사용하세요. 브랜치는 변경을 나누는 작업선이고, 별도 작업 공간은 다른 이슈의 파일과 섞이지 않는 폴더입니다. 기본 브랜치 `main`이 아닌지, 다른 작업과 공유하지 않는지, 미완료 변경이 있는지 먼저 확인하세요. 기존 폴더를 공유하는 방식이라면 변경 전에 알리고 분리하세요.
4. 구현 전에 에이전트가 설명한 작업 범위와 검증 방법을 확인하세요. 구현·검증 후 학생이 PR(변경 검토 요청)을 만들도록 요청하거나 직접 만드세요. PR 양식에 연결 이슈·완료 조건·검증 결과·실제 확인 순서를 적으세요.
5. 앱에서 `student-reviewer`를 선택해 검토를 요청하세요. 검토 대상 PR의 변경 내역·관련 코드·이슈 완료 조건에 접근 가능한지 확인하고, 접근하지 못하면 필요한 자료를 제공하세요. 비밀정보나 개인정보는 빼세요. 지적을 수정한 뒤 필요한 검사를 다시 수행하고 재검토하세요.
6. 학생은 앱을 직접 실행해 PR에 적힌 순서와 기대 결과를 확인하고, **학생 확인란을 본인이** 체크하세요. 실행 방법이 아직 없으면 확인 완료로 표시하지 말고 미검증 사유를 남기세요.
7. GitHub의 필수 검사·사람 승인·브랜치 보호 조건을 충족했는지 확인한 뒤 권한 있는 학생 또는 담당자가 머지하세요. 머지는 기본 브랜치에 변경을 합치는 작업입니다. 에이전트에게 맡길 때도 명시적으로 허용한 범위에서만 진행하세요.

비밀번호·API 키·개인정보는 코드·로그·이슈·PR·스크린샷에 넣지 마세요.
로그인·권한·개인정보·결제·데이터 삭제·배포 설정 변경은 영향과 위험을 설명받고 진행 여부를 결정하세요.

## 파일로 준비된 부분

| 파일 | 역할 |
| --- | --- |
| `.github/copilot-instructions.md` | 작업 범위·안전·검증·한국어 소통·머지 원칙 |
| `.github/agents/student-reviewer.agent.md` | 이슈 기준으로 검토하는 읽기 전용 리뷰어 |
| `.github/ISSUE_TEMPLATE/feature.yml` | 기능 요청과 완료 조건 입력 양식 |
| `.github/ISSUE_TEMPLATE/bug.yml` | 버그 재현 순서와 기대 결과 입력 양식 |
| `.github/pull_request_template.md` | 검증 근거와 에이전트·학생 확인을 분리한 PR 양식 |
| `README.md` | 학생 작업 흐름과 관리자의 별도 설정 안내 |

## 사람이 GitHub에서 별도로 구성할 부분

- 이 파일들을 검토해 기본 브랜치에 반영해야 팀이 기본 양식·지침으로 사용할 수 있습니다. 팀원의 저장소 접근 권한과 이슈 담당자 지정도 사람이 관리하세요.
- 저장소 설정의 규칙 세트(Rulesets) 또는 브랜치 보호에서 `main`에 PR을 통한 변경과 사람 승인을 요구하도록 구성하세요. 팀 상황에 맞는 승인 수를 정하고, 새 변경 후 재승인·검토 대화 해결 요구도 검토하세요. 직접 푸시와 우회 권한도 점검하세요.
- 현재 자동 검사(CI)와 필수 검사 이름은 없습니다. 기술 스택이 정해진 뒤 실제 검증 명령을 실행하는 GitHub Actions 등의 검사를 마련하고, 실제 생성·실행된 검사 이름을 보호 규칙의 필수 검사로 지정하세요. 존재하지 않는 검사 이름을 추측하지 마세요.
- 학생의 수동 확인은 PR에 증거를 남기는 팀 절차입니다. 체크박스만으로 GitHub가 머지를 차단하지 않습니다. 사람 리뷰어가 확인하세요.
- 자동 리뷰·자동 머지를 원한다면 지원 범위와 정책을 먼저 확인해 별도로 설정해야 합니다. 이번 작업에서는 저장소 설정을 변경하지 않았고 자동화도 추가하지 않았습니다.

**리뷰 에이전트 파일만으로 PR 자동 리뷰가 실행되거나, 머지가 차단되거나, 자동 머지가 활성화되지는 않습니다.**
에이전트의 “문제 없음” 판정은 GitHub의 공식 승인이나 머지 허가가 아닙니다.

## 지원 확인 범위와 제한

- [공식 에이전트 형식 문서](https://docs.github.com/en/copilot/reference/custom-agents-configuration)에서 확인한 `name`·`description`·`tools`만 사용했습니다. 도구는 읽기·검색 별칭인 `read`·`search`로 제한했고, 셸 실행·수정·다른 에이전트 호출·게시 도구는 허용하지 않았습니다.
- [앱 공식 안내](https://docs.github.com/en/copilot/how-tos/github-copilot-app/customize-github-copilot-app)는 사용자 지정 에이전트 선택 기능을 설명합니다. 다만 현재 설치된 앱에서 이 파일이 실제로 인식되는지, 도구 제한이 적용되는지, PR·이슈에 접근할 수 있는지는 실행 검증하지 못했습니다. 사용 전 앱의 에이전트 목록과 허용 도구를 확인하고, 제한이 적용되지 않으면 리뷰에 사용하지 마세요.
- 읽기·검색만으로는 테스트 실행이나 GitHub 리뷰·댓글 게시를 할 수 없습니다. 리뷰어는 실행했다고 주장하지 않으며, 게시 요청을 받아도 초안만 제공하고 권한 있는 사람이 게시합니다. PR 변경 내역이나 이슈를 읽을 수 없으면 학생이 필요한 자료를 제공해야 합니다.
- 조직 정책·계정 요금제·저장소 권한에 따른 보호 규칙, 공식 리뷰, 자동 리뷰·자동 머지의 사용 가능 여부와 현재 설정은 확인하지 않았습니다.
- 작성 환경에 Python과 사용 가능한 YAML 파서가 없어 양식의 자동 구문 검증은 수행하지 못했습니다. 기본 브랜치 반영 후 GitHub에서 이슈 양식의 표시와 필수 입력 동작을 확인하세요.
- 앱 전용 실행 스크립트·자동화 설정 파일인 `.github/github-app.yml`은 추가하지 않았습니다. 확인된 실행 명령이 없고 자동화 설정도 요청 범위에 없기 때문입니다.

## 학생의 첫 요청 예시

> 이슈 #번호를 확인하고 작업 범위와 검증 방법을 설명한 뒤 구현해줘.

> student-reviewer로 현재 변경 사항을 이슈 #번호의 완료 조건에 맞춰 검토해줘.

`#번호`는 실제 이슈 번호로 바꾸세요. 위 문장은 자연어 요청이며, 특정 명령이나 자동 호출을 보장하지 않습니다. 실제 에이전트 선택·호출 방식과 선택된 에이전트는 앱에서 확인하세요.
